## Overview

ApproveDesk already notifies people by **in-app inbox** and **email**. Mail copy is hardcoded in `App\Notifications\*`. There is no channel interface, no admin channel screen, and no WhatsApp or Telegram send path.

Phase 8.2 keeps email and in-app as **generic** delivery that works on a stock install. Administrators may **optionally** turn on Microsoft Teams, Slack, WhatsApp, and Telegram, and may **optionally** override generic email copy. WhatsApp outbound uses **WhatsApp Business Platform template mapping**, not free-form text.

Users still only choose **when** email is sent (`Settings → Notifications`: immediate / daily / weekly / in-app only). They do not paste bot tokens.

| Surface | Who | Default | Purpose |
|---|---|---|---|

| SMS | Channel interface only | Off | Not in this administrator-options set (phone already stored) |

**Fail-open on optional channels:** a missing token, unmapped WhatsApp template, or unlinked Telegram account skips that channel. Email and/or in-app still go out. Workflow state does not depend on chat delivery.

## Channel interface (P8-NOT-01)

Introduce a small contract so new drivers do not edit every notification class:

```php
interface NotificationChannel
{
    public function key(): string;

    public function isConfigured(): bool;

    public function canReceive(User $notifiable): bool;

    public function send(User $notifiable, OutboundNotification $message): void;
}
```

`OutboundNotification` is a DTO: `kind`, `subject`, `lines`, `actionUrl` (nullable), `actionLabel` (nullable), `payload` (submission id, reference, title, …).

Registry selects drivers from `via()` plus org enablement:

1. Always consider `database`.
2. Consider `mail` unless the user is `in_app_only` (digests unchanged).
3. Consider Teams / Slack / WhatsApp / Telegram only when the org enabled that option **and** `isConfigured()` **and** `canReceive()`.
4. Queue each send on the database driver. Do not add Redis.

Existing Laravel `Notification` classes stay the event source. They build the DTO (from generic copy or a published email template) and hand it to the registry. They do not call Graph or Bot APIs themselves.

Secrets live in `config/services.php` + encrypted `settings` keys. Never log tokens. Never bind tokens on Livewire public properties.

## Administrator screen

New admin page, gated by `settings.manage` (same as branding / approval settings):

**Settings → Notification channels**

Not the personal `settings/notifications` page.

Sections:

1. **Email templates** — list of `kind`s, edit, preview, restore default, publish.
2. **Microsoft Teams** — enable, app/bot credentials, test, status.
3. **Slack** — enable, bot token + signing secret, test, status.
4. **WhatsApp** — enable, WABA id, phone-number id, access token, **Fetch templates**, mapping table, test (optional send to a staff phone).
5. **Telegram** — enable, bot token, webhook URL (derived from `APP_URL`), deep-link instructions, test.

Each optional channel has: enabled flag, last successful test timestamp, last error (redacted). Disable flips `enabled` without deleting credentials.

Help: new article under Administration; definitions for channel, email template, WhatsApp template mapping, Telegram bot. Update `organization-settings` and `account-settings` so personal frequency is not confused with org channels.

## Editable email templates (P8-NOT-04)

Generic PHP copy remains the **fallback**. Administrators publish an override per `kind`. Unpublished or restored kinds use generic copy.

Stored fields (new table, e.g. `notification_email_templates`):

- `kind` (unique in this single-org product)
- `subject`
- `body` (plain text or a small allowed markdown subset; sanitize like other rich text if HTML is allowed)
- `updated_by`, `updated_at`
- `is_custom` (false after restore)

Merge fields (exact tokens; unknown tokens stay literal):

| Token | Source |
|---|---|
| `{{recipient_name}}` | User name |
| `{{reference_number}}` | Submission |
| `{{title}}` | Submission |
| `{{submitter_name}}` | Submitter |
| `{{priority}}` | Submission |
| `{{decision}}` | Decided notifications |
| `{{comment}}` | Reason / nudge note |
| `{{approval_url}}` | `ApprovalLinks::confirmationUrl()` — action-required only |
| `{{submission_url}}` | `route('submissions.show', …)` |

Rules:

- Saving an **action_required** template without `{{approval_url}}` is a validation error.
- Publishing does not change signed-link lifetime or stale-step policy.
- Preview renders with sample data; it does not send.
- No per-request-type email templates in 8.2 (one org, one copy per `kind`).
- Localization of templates is out of scope (`ROADMAP.md`).

## WhatsApp Business template mapping (P8-NOT-04)

Meta does not allow free-form business-initiated messages outside the 24-hour session window. ApproveDesk therefore **never** sends `type: text` for these notifications. It sends `type: template` only.

### Credentials

Environment / encrypted settings (names indicative):

- `WHATSAPP_WABA_ID`
- `WHATSAPP_PHONE_NUMBER_ID`
- `WHATSAPP_ACCESS_TOKEN`

Provider is the official Cloud API. A later BSP (Twilio, Africa’s Talking) can implement the same mapping contract with a different HTTP adapter. CI never calls live Graph.

### Fetch

Administrator clicks **Fetch templates** (also a scheduled refresh, e.g. daily via existing cron).

`GET /{WABA_ID}/message_templates`

Cache locally (`whatsapp_message_templates`):

- Meta template name
- language
- status
- category
- component JSON (header/body/buttons and placeholder count)

Keep rejected/paused rows so a mapping can show “no longer approved” instead of silently disappearing.

### Map

Table `whatsapp_notification_maps`:

- `kind` (ApproveDesk notification kind)
- `template_name`
- `language`
- `bindings` JSON: ApproveDesk slot → template placeholder (`{{1}}` or named)

Each `kind` has a **required slot list** in code. Example `action_required`: `recipient_name`, `reference_number`, `title`, `submitter_name`, `approval_url`.

Admin UI: pick an **APPROVED** template from the fetched catalog; bind each required slot to a placeholder. Save is rejected if placeholder count is too small or the template is not approved.

Enabling WhatsApp does **not** require every `kind` to be mapped. Unmapped kinds skip WhatsApp.

### Send

When the registry chooses WhatsApp:

1. User has valid E.164 `phone`.
2. Mapping exists and cached template status is `APPROVED`.
3. POST `/{PHONE_NUMBER_ID}/messages` with template name, language, and bound parameters.
4. On 4xx “template not found / paused”, mark mapping unhealthy and skip; do not retry as text.

URL buttons on the Meta template should use the signed **confirmation** URL (or a documented dynamic suffix). Opening WhatsApp must not approve. In-chat Approve/Reject on WhatsApp is out of 8.2.

Delivery receipts and retries are the rest of P8-NOT-04; the mapping work can land in the same task group as email templates.

## Telegram (P8-NOT-01)

Telegram allows free-form bot messages. No Meta-style template catalog.

### Credentials and hosting

- Admin pastes a **bot token** from BotFather.
- ApproveDesk registers a **webhook** on a public HTTPS `APP_URL` route (e.g. `/integrations/telegram/webhook`).
- **Do not long-poll.** Shared hosting has no persistent worker for `getUpdates`.

Verify inbound webhook secret/token. Throttle. Do not run workflow mutations from Telegram in 8.2 (notify only).

### Identity

`users.telegram_user_id` nullable unique.

On personal account settings, if the org enabled Telegram: “Link Telegram” shows a `https://t.me/<bot>?start=<signed-one-time-token>` link. The webhook maps `start` payload → user id, stores `telegram_user_id`, and replies that linking succeeded. Unlink clears the column.

`canReceive()` is true only when linked and the org channel is enabled.

### Send

Bot API `sendMessage` with text derived from the same `OutboundNotification` DTO as email (generic copy or email-template body, converted to Telegram text). Include `submission_url` or `approval_url` as a URL. HTML parse mode only if sanitized.

Inline-keyboard Approve/Reject is **not** in 8.2. If added later, it must reuse P8-NOT-02 signed action state and the email stale-step policy.

## Teams and Slack

Unchanged from the original P8-NOT-01/02 intent:

- Admin option: credentials + test.
- Interactive cards with **signed action payload**.
- Inbound HTTP from Slack/Teams; verify platform signature; then verify ApproveDesk token.
- Same checks as `EmailApprovalController`: expiry, current step, assignee/delegate, `WorkflowEngine::processAction()`.
- GET/message delivery never mutates workflow.

Identity mapping (Slack member id / Teams user id) is required for `canReceive()`. Email-match as a convenience is allowed only after the org option is on; do not DM strangers.

## Tests (8.4 additions)

All HTTP to Meta/Slack/Teams/Telegram/Twilio faked. SQLite in-memory.

- Unconfigured WhatsApp/Telegram/Teams/Slack: notification still stores database + mail.
- Email template override changes subject/body; restore default returns generic copy.
- Action-required custom template without `{{approval_url}}` fails validation.
- Rendered action-required mail still produces a signature that `EmailApprovalTest` would accept.
- WhatsApp fetch stores catalog; mapping to a non-approved template fails; send with mapping posts `type=template`; unmapped kind does not POST.
- Telegram send hits faked `sendMessage` only when `telegram_user_id` is set; long-poll code is absent.
- Tamper/stale tests remain P8-NOT-02 for Teams/Slack/email.

## Key decisions

1. **Email + in-app are generic.** Optional channels never replace them as the reliability baseline.
2. **WhatsApp is template-mapped, not free-form.** Matches Meta rules and the requested WABA mapping.
3. **Email templates are ApproveDesk-owned copy.** Distinct from WhatsApp templates.
4. **Telegram is notify-only in 8.2** (webhook + signed URL). Interactive decisions stay Teams/Slack.
5. **Skip, don’t fail** when an optional channel is off, unmapped, or unlinked.
6. **Webhook, not long-poll**, for Telegram (shared hosting).
7. **SMS and web push stay in the interface** but are not admin options in this set.
8. **`in_app_only` still means “no workflow email.”** It does not mute WhatsApp/Telegram. Document that.
